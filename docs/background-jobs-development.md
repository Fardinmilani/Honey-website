# Background Jobs Development

Phase 16 adds a headless Nest application context in `apps/worker`. It consumes
BullMQ jobs over Redis and calls the same `packages/backend` application
services used by the API. The worker does not import `apps/api`, `apps/web`, or
`packages/db`, and it makes no internal HTTP calls to the API. PostgreSQL and
Redis are supplied by the local Docker stack; `docker/worker.Dockerfile` builds
the optional worker image with no published port.

## Capability map

The shared job envelope and names live in `packages/backend/src/jobs`. Only
jobs with an existing application capability have active consumers.

`outbox`, `email`, `sms`, `inventory`, `orders`, `payments`, `media`, `search`,
`cache`, and `maintenance` are centrally registered even when a queue has no
active processor. The worker never creates a fake task merely to occupy a queue.
Hero media is outside object storage and all media jobs.

## Contracts, producers, and routing

Every job is a plain-JSON V1 envelope with `version`, `type`, `correlationId`,
`occurredAt`, and a narrowly validated payload. An optional `eventId` links an
outbox job to its committed event. Runtime decoding rejects extra fields,
malformed values, and unknown versions before any service call. The V1 decoder
and synthetic previous-release fixture remain as a compatibility contract; a
breaking change requires a separate V2 decoder rather than changing V1 meaning.
Job IDs are deterministic from the logical event or UTC schedule bucket and
contain no recipient or provider data. BullMQ deduplication complements the
backend's transaction, lock, and delivery-record idempotency.

Outbox producers remain inside backend business transactions. The dispatcher
claims a bounded batch with PostgreSQL row locking and a lease, routes only
explicitly supported event types, enqueues each downstream job with a stable
ID, then marks the event dispatched. If Redis is unavailable, the original
business commit is unaffected and the event remains eligible for retry. If
enqueue succeeds but confirmation fails, the lease expires and a second
dispatch uses the same job ID; the consumer application service still has to
be idempotent. This is at-least-once transport with one logical domain effect,
not a claim of distributed exactly-once delivery.

Known events with no Phase 16 consumer are recorded as deferred quarantine so
they do not occupy every polling batch. Unknown type/version is a distinct
quarantine failure with durable operational visibility. Neither is silently
marked dispatched. The catalog and shipment event routes are listed and tested
in the worker's explicit routing table.

## Execution policy

Processors deserialize, validate, establish correlation and trusted execution
context, call one backend application service, and classify the outcome. They
contain no reservation, payment, inventory, sitemap, or notification rules.
Inventory reconciliation uses a narrow `SYSTEM` / `WORKER` context and the same
service used by authorized staff; anonymous and customer contexts cannot enter
that path. The worker never creates a staff user. Scheduled reconciliation does
not automatically repair stock. Each system invocation scans at most 100 merged
inventory and incoming-projection keys, returns at most 400 field drifts, and
provides a validated keyset cursor only when a lookahead finds more keys. The
worker enqueues that cursor as a follow-on job with an ID derived from the
parent job and cursor, so replay deduplicates without colliding with a later
scheduled scan. Redis stores a bounded count summary rather than drift rows.
Changes inserted before the
cursor during a scan are covered by the next scheduled scan; only authorized
staff may request a repair.

Retries use bounded attempts and exponential backoff with jitter. Permanent
validation, version, authorization, and invariant failures do not retry;
transient network, provider, Redis, or database failures may retry. Final
failure persists only safe metadata in PostgreSQL `JobFailure`, keyed by queue,
job ID, and terminal cycle; a structured high-severity operational event is
emitted once. Raw payloads, provider responses, email, phone, addresses,
tokens, and secrets are absent from the durable failure record and logs. Redis
completed/failed retention is bounded. Queue metrics report waiting, active,
delayed, completed, failed, and unresolved dead-letter counts by queue, plus
outbox pending age/count where available; they carry no customer labels.

The worker registers its own repeat schedules through BullMQ. Re-registering
on restart or across instances creates one logical schedule per definition.
Cadence only determines when a service checks eligibility; it does not change
reservation TTL, payment rules, or inventory math. Queue concurrency is bounded.
On SIGTERM/SIGINT, the worker stops taking new work, closes schedulers and
queues, waits for active work within the configured grace, and closes Nest and
Redis resources. Work interrupted after the grace remains recoverable through
BullMQ redelivery and backend idempotency.

## External boundaries

Sitemap regeneration uses a backend port and a worker-side adapter pointing to
a fixed configured web origin and fixed authenticated endpoint. The secret is
resolved from server configuration, never from a job. Production requires an
HTTPS origin. Jobs cannot supply a URL, preventing arbitrary fetches. The web
endpoint allows only the existing `fa` and `en` locales. A sitemap job refreshes
the requested locale's data tag without invalidating the other locale's catalog
cache; catalog outbox changes can still invalidate shared catalog tags.

The Phase 15 shipment mailer resolves recipient and locale from authoritative
backend data after the outbox event commits. SMTP has no transactional
acknowledgement shared with PostgreSQL: a process crash after SMTP accepts mail
but before `sentAt` is recorded can cause a duplicate external message. The
durable delivery claim limits this risk, while the application delivery record
is idempotent. No mathematical exactly-once SMTP guarantee is claimed.

Backup verification follows [ADR-0041](adr/0041-backup-verification-phase-boundary.md).
`BACKUP_VERIFICATION_ENABLED=false` is the only valid current setting. Startup
reports the capability as deferred; no executable schedule is registered and
no fake success adapter exists. Phase 20 adds the real backup system, concrete
verification adapter, enablement, and restore drill. No production backup,
PITR, retention, or off-host storage is implemented here.

## Local operation

Start the Docker infrastructure with `pnpm docker:up`. Host execution uses
`pnpm worker:dev` after the database migrations and a server-only
`WEB_REVALIDATE_SECRET` are configured. `WORKER_WEB_ORIGIN` is a fixed origin;
the optional Compose `worker` profile overrides it for a web process on the
Docker host. `docker compose --profile worker up --build -d worker` starts one
container without a public worker port. `pnpm worker:docker:build` builds the
same production-style image separately. The `--healthcheck` command probes
Redis queue connectivity only; process boot and `worker.started` confirm the
Nest context and schedules. Neither exposes HTTP.

After building the image, `pnpm worker:smoke:sigterm` creates a temporary
migrated PostgreSQL database and isolated Redis queues, starts the worker
container, holds a sitemap revalidation request while its job is active, and
sends Docker SIGTERM. It checks clean exit and completed BullMQ state, then
removes its temporary database, queues, and container. CI runs the same smoke
against the host-network service containers.

The `.env.example` file documents schedule intervals, batch limits, queue
prefix, and shutdown grace. Redis job keys use the worker prefix, separate from
session and rate-limit keys. A worker running in production fails closed on
invalid Redis, web origin, or capability configuration. Secrets are provided at
runtime, never embedded in an image or queue payload.

Phase 17 may later provide authorized operational UI; no queue control API is
added here. Phase 19 owns full tracing and monitoring products. Phase 20 owns
production deployment and backup hardening.
